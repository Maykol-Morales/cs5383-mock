Mock.

El doble de prueba que verifica comportamiento, no estado.

Definición

Un doble preprogramado con expectativas

Qué método

Debe llamarse el método esperado.

Con qué argumentos

Y con los valores correctos.

Cuántas veces

Una llamada de más o de menos hace fallar el test.

Verifica comportamiento (interacciones), no estado.

[Michael · 1:00] Un Mock es un doble de prueba preprogramado con expectativas: qué métodos deben llamarse, con qué argumentos y cuántas veces. Si recibe una llamada que no esperaba, o no recibe una que sí esperaba, el test falla. Frase clave para que se queden: el Mock verifica comportamiento, es decir interacciones; no verifica estado ni el valor de retorno.

Problema y uso

Hay efectos que no dejan rastro en el resultado

El problema

Enviar un email, cobrar un pago, escribir un log. Un assert sobre el valor de retorno no los detecta.

Se usa cuando

  • Importa que se llame a la colaboración: gateway.cobrar(100) una sola vez.
  • La dependencia es lenta, no determinista o con efectos reales (red, BD, correo).
  • No hay estado observable que revisar.

Cuidado. Acopla el test a la implementación. Si basta verificar estado, no lo uses.

[Michael · 1:00] El problema: hay efectos del código bajo prueba que no se ven en el valor que devuelve. Mandar un correo, cobrar un pago, escribir un log. Un assert sobre el resultado no los detecta. Usamos un Mock cuando lo que importa es que se llame a una colaboración, por ejemplo gateway.cobrar(100) exactamente una vez, y cuando la dependencia es lenta, no determinista o tiene efectos reales como red, base de datos o correo. Advertencia: el Mock acopla el test a la implementación. Si alcanza con revisar el estado, no abusen. Paso la palabra a Sebastián.

Comparación

Mock frente a Dummy, Stub, Fake y Spy

DobleQué haceQué verificaEjemplo
DummyRellena un parámetro; nunca se usaNadanew Servicio(null, dummyLogger)
StubDevuelve respuestas enlatadasNada (se revisa el estado del SUT)when(repo.buscar(1)).thenReturn(user)
FakeImplementación real simplificadaNada (se revisa el estado)repo = new RepoEnMemoria()
SpyStub que registra cómo lo llamaronLlamadas, después de ejecutarverify(spy).enviar("hola")
MockPreprogramado con expectativasLlamadas, argumentos y veces; falla si no se cumplenverify(gateway, times(1)).cobrar(100)

El Mock verifica comportamiento. El Stub solo devuelve datos.

[Sebastián · 1:15] Para ubicar al Mock entre sus primos. Dummy: rellena un parámetro y nunca se usa. Stub: devuelve respuestas enlatadas. Fake: una implementación real pero simplificada, como un repositorio en memoria. Spy: un stub que además registra cómo lo llamaron, y se verifica después de ejecutar. Mock: viene preprogramado con expectativas sobre llamadas, argumentos y veces, y falla si no se cumplen. Idea central: el Mock verifica comportamiento; el Stub solo devuelve datos. Según Fowler, un Mock es un tipo de Spy, un Spy es un Stub, y un Stub es un Dummy; el Fake es distinto.

El mesero y la comanda

¿Entregó la comanda exactamente una vez y con el pedido correcto?

Dos veces, se prepara doble. Ninguna, tu comida nunca llega. No evaluamos el plato.

[Sebastián · 0:45] Piensen en un restaurante. El mesero toma el pedido y debe pasarlo a cocina. No nos interesa cocinar de verdad; la cocina es un actor de utilería que solo anota qué le llegó. Lo que verificamos: que la comanda llegó una sola vez y con el contenido correcto. Si llega dos veces, se prepara doble; si no llega, nunca come nadie. Fíjense: no estamos mirando el plato, estamos mirando la interacción.

Ejemplo en software

Confirmar una orden envía un correo

from unittest.mock import Mock

def test_confirmar_orden_envia_un_correo():
    email = Mock()                    # no envía nada real
    service = OrderService(email_service=email)

    service.confirm(Order(id=1, customer="ana@mail.com"))

    email.send.assert_called_once_with(
        to="ana@mail.com", subject="Pedido 1 confirmado"
    )

Sin el mock, cada corrida enviaría correos reales: spam, costos y tests lentos. Con el mock, el test es rápido, determinista y aislado.

[Sebastián · 1:00] OrderService debe avisar al cliente cuando se confirma una compra, llamando a EmailService.send. En el test reemplazamos EmailService por un Mock. Ejecutamos confirm y después verificamos con assert_called_once_with: una sola llamada, al correo y con el asunto correctos. Qué evita: sin el mock, cada ejecución de la suite mandaría correos reales a clientes, con costo, lentitud y dependencia de la red o del SMTP. Lo que verificamos es una interacción, no un valor de retorno. Michael nos muestra esto corriendo.

Demo · demo_mock.py

Código 
class OrderService:
    def __init__(self, email):
        self.email = email
    def place(self, user, total):
        if total <= 0:
            return False
        self.email.send(user, f"Pedido de {total} confirmado")
        return True

# setUp: self.email = Mock()
def test_pedido_valido_envia_correo(self):      # PASA
    self.svc.place("ana@x.com", 50)
    self.email.send.assert_called_once_with(
        "ana@x.com", "Pedido de 50 confirmado")

def test_pedido_invalido_no_envia(self):       # PASA
    self.svc.place("ana@x.com", 0)
    self.email.send.assert_not_called()

def test_falla_a_proposito(self):              # FALLA
    self.svc.place("ana@x.com", 50)
    self.assertEqual(self.email.send.call_count, 2)
Salida 
test_falla_a_proposito ... FAIL
test_pedido_invalido_no_envia ... ok
test_pedido_valido_envia_correo ... ok

AssertionError: 1 != 2

Ran 3 tests in 0.001s
FAILED (failures=1)

Esperaba 2 envíos, hubo 1. El Mock contó las llamadas.

[Michael · 1:30] Demo con unittest.mock. OrderService recibe el servicio de correo inyectado. Si el total es cero o negativo no envía; si es válido, envía un correo. Test 1: pedido válido, verifica que send se llamó una vez con esos argumentos. Pasa. Test 2: pedido inválido, verifica assert_not_called. Pasa. Test 3 es el que falla a propósito: ejecutamos un solo pedido pero esperamos dos envíos. Salida: AssertionError 1 distinto de 2, FAILED con una falla. Lo importante: el test falla por comportamiento, por la cantidad de llamadas, no por ningún valor de retorno. Ese es el trabajo del Mock. (Si hay tiempo, correr python demo_mock.py en vivo.) Conclusiones

Un Mock responde: ¿se colaboró como se esperaba?

  • Verifica llamadas, argumentos y veces. No estado.
  • Útil cuando el efecto no aparece en el resultado y la dependencia es lenta o real.
  • Si basta mirar el estado, prefiere Stub o Fake. Un Mock de más acopla el test a la implementación.
[Sebastián · 0:45] Para cerrar. Un Mock responde a una pregunta: ¿el código colaboró como esperábamos? Verifica llamadas, argumentos y cantidad de veces, no estado. Es útil cuando el efecto no se ve en el resultado y la dependencia es lenta, no determinista o tiene efectos reales. Y la advertencia final: si basta mirar el estado, usen Stub o Fake; demasiados mocks atan el test a la implementación. Gracias. Quedamos atentos a preguntas.
